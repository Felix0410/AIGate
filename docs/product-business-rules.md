# AIGate — Enterprise AI Agent Governance: Confirmed Business Rules

> 总控维护的产品业务规则事实来源。2026-10-20 用户完成七项主体/额度/模型原则确认，**不等于相关功能已经实现**。仍有业务细则需要逐层讨论；Phase 4 编码保持 PAUSED。
>
> 项目定位：企业内部已有 Agent 的统一 AI 模型调用网关、员工额度/团队资源管理、模型安全准入与流量治理系统。AIGate 负责管理 Agent 的接入与模型流量，**不开发 Agent、不建设 Agent 注册细节、工作流编排器或 Agent 执行引擎**。

## 1. Confirmed Top-Level Principles

1. **统一网关入口**：纳入管理的企业 Agent 调用大模型必须经过 AIGate；这是公司治理规则，后续还需要凭证/网络出口等机制落实，不能声称软件接口天然杜绝绕过。
2. **员工+团队**：员工有一个主团队；有时被邀请参与其他团队任务，可以因此获得更多额度。员工可向团队申请或由团队主动发放额外额度；额度发放后归员工可用，模型请求不再需要每次判断由哪个团队承担费用。发放来源需保留审计记录。
3. **Agent 纳管方式**：Agent 业务由外部系统开发/注册与运行，平台管理员统一管理纳管范围、接入规则/额度相关策略；不开发 Agent 注册的业务细节。
4. **Agent—Application**：按用户选择采用一对一；当前 Application 可以作为每个受管 Agent 的网关调用身份与规则载体。当前 Application 的 API Key 认证只证明 Agent/Application，不证明员工本人。
5. **调用人**：普通模型调用必须归属实际员工，额度按实际员工计算；定时/无人值守任务允许专门开账号进行独立管理。员工在调用 AIGate 时必须额外携带个人认证凭证，用于核验真实员工身份并决定扣费；Agent 自身 Application API Key 只能认证 Agent，不可替代员工凭证。无人值守任务可单独使用专用员工账号，生命周期与授权仍需落实。
6. **周额度制度（已确认方向）**：有使用权限的员工使用不同 Agent 时有免费额度；先用对应 Agent 免费额度，超出后使用员工个人额度；个人额度不足可以向团队申请额外额度。已确定每个有使用权限的员工 × Agent 拥有独立免费额度、固定周周期统一重置，个人基础额度亦按周重置，团队补充额度按独立额度和有效期管理；具体周起点/时区/金额/分配和结算事务仍待确认。
7. **紧急任务**：针对具体任务申请临时额外额度和有时效的优先处理权。优先处理需真正的容量/调度约束支持，不能仅存一个 priority 字段。
8. **模型权限**：每个 Agent 有几个由管理策略指定的允许模型选项，由员工在该 Agent 允许范围内手动选择；涉及安全与业务需求。
9. **路由语义**：自动路由主要用于**同一逻辑模型的多个 Deployment** 之间选择，不是在不同模型之间自行切换。当前 P2 仅有 Application.defaultDeploymentId，未来扩展要保留允许模型限制和逻辑模型选择的分离。
10. **模型价格与运行压力**：各模型有不同计费规则；管理员需要看到按模型运行压力与健康状态。网关能够观测自身请求量、延迟、并发、错误、Provider 限流，但不天然知道第三方 Provider 的实际 GPU 负载。

## 1.1 Confirmed Weekly Quota & Identity Details（2026-10-20）

来自用户第二轮六项明确选择，**是已确认业务规则，但目前没有代码实现**。

1. **每员工×每 Agent 的独立免费周额度（1A）**：员工只要获授权使用该 Agent，就拥有该 Agent 自身的一份个人免费额度；不是团队共享/公司共享免费池。不同 Agent 的免费额政策可由管理配置确定；不同团队使用该 Agent 有差异化额度的具体适用规则待确认。
2. **统一周周期（2A）**：每周固定时刻刷新，不滚动7天，未用免费/基础额度不自动累计。准确周起点、企业时区、周内配置调整与重置时刻尚需确认。
3. **个人基础额度与团队补充额度（3C）**：员工个人的基础额度按周刷新；团队批准或主动发放的额外额度按笔有独立额度与有效期，不被统一周刷新直接清零（除非该笔发放本身到期）。
4. **团队额度池的自主调配（4，用户自由补充）**：每个员工仍有正常个人额度；个人需要更多可以向团队申请，团队也能主动发放。额度发放/受领应有来源、批准人、数量、有效期等可追溯记录；**发放后模型调用直接消耗员工可用额度，不必在每次调用重新判断由哪个团队承担**。为防止双重消费，团队侧需避免同一笔补充额度重复分配，但“发放即从团队池扣除”“额度用完才按实际使用扣团队池”及到期未用部分返还规则尚需明确。
5. **统一内部积分（5B）**：不同模型按实际 Token 使用情况与各自价格换算内部点数，消耗各额度桶中的点数。具体输入/输出/缓存 Token 价格、舍入、币种与价格版本待定。
6. **员工独立认证凭证（6B）**：Agent 用自己的 Application API Key 证明 Agent 身份，员工调用时还应向 AIGate 提供独立个人凭证，由 AIGate 校验真实身份、授权 Agent 使用权限与归属。禁止只接受未签名 employeeId；暂时不指定 token 类型或系统外 SSO 协议。自动任务允许独立专用账号。

**目标用量扣减顺序（由已确认规则得到）：** 首先消耗 employee×Agent 免费周额度，超过后使用员工本周个人基础额度，仍不足时使用员工已获批准/主动发放的有效补充额度；不足时拒绝或进入申请流程。一次调用若跨多个额度桶消费，原子性与实际结算算法留待下一层确认。

**强调：** 用户认为“团队负责发额度即可，不必每次模型调用考虑费用承担方”，但团队发放本身仍然是需要准确入账、审批和审计的资源转移事件。这一点不代表必须在每次调用查团队账本。

## 1.2 2026-10-20 — Confirmed Billing Rules and Depleted-Quota Handling

本节为用户最新六项确认，优先于前文历史性“待确定”的对应说法，目标业务规则不等于已实现代码。

1. 周起点（week=A）：公司统一时区，每周一 00:00 统一刷新员工×Agent 免费额度和员工个人基础额度；未用免费额度及基础额度不滚存。具体公司时区、跨周在途结算留待明确。
2. 团队发放（grant=C）：员工申请获批或团队主动发放时，立刻从团队额度池扣减相应积分，并在员工名下形成有独立有效期的补充额度；到期未用部分作废，不返还团队池。发放与实际模型消耗是两种事件；需防重复发放/重复扣减并保留流水。
3. 模型定价（price=A）：按不同模型的输入/输出（以及有差异价格时的缓存等）Token 量和价目换算企业内部积分。具体单价版本、精度、舍入和结算策略待后续确定。
4. 失败计费（failure=A）：只有确认实际用量时才按实际用量结算；失败或超时导致无法确定真实用量时标记“待核对”，而不是虚构用量。预留额度和待核对期间如何处理需另行确认。
5. 余额不足（insufficient=A + 后置补充覆盖）：最终确认不直接因积分不足拒绝正常受权请求，而是降到最低速率、最低优先级并通知员工，努力保留基本可用性。不能据此推导出无限免费调用；模型不可用/权限不符/总保底容量耗尽等异常仍有拒绝或等待可能。
6. 调用结算（reserve=A）：模型出站前预留受控的预估/最大调用成本，结束后按可验证的实际成本结算，释放未使用的预留。如何估算上限、跨余额来源预留、失败未知用量对账另行确定。

已确认的正常消耗顺序：员工×当前 Agent 免费周积分 → 员工跨 Agent 基础周积分 → 员工获发放且有效的团队补充积分 → 耗尽后进入受限保底服务（具体资金来源尚未决定）。

### Critical unresolved business conflicts

- 积分为零仍允许消耗收费模型，与“出站前预留”之间缺少资金来源。候选为企业出资的、有限量的保底资源池，伴随最低速率/并发/优先级，尚未获用户批准。单纯降速只能限成本增长速度，无法限制累计成本。
- 最低优先级不等于保证响应；若要求繁忙时仍有最低服务能力，需明确预留基础并发、等待时间和 Provider 不可用时的例外。
- Provider 超时可能已产生实际用量；未知用量须可对账，P3 best-effort InvocationRecord 不是准确费用账本。
- 团队发放即扣池且到期不返还，可能引发未使用积分作废；界面须能区分已发放、实际消费、到期失效和团队池余额。

后续层级待确认：保底出资方及每日/周/员工上限、保底可选模型与容量、紧急任务优先级与排队、同逻辑模型部署路由/健康观测、价格版本及未知用量对账。

执行状态：Phase1~3 CLOSED；P4-T01 PAUSED / NO CODING。历史 Application RPM token-bucket 方案及 ADR-004 仍是待复核候选。

## 1.3 Confirmed Traffic Tiers, Fallback Service, Deployment Routing & Capacity Observability（2026-10-20）

以下来自用户第三轮六项正式业务确认。**目标业务已确认，不代表已实现，Phase 4 仍暂停。**

1. **企业统一保底资源（1A）**：员工全部正常额度耗尽后，企业公共预算为每员工提供**按周有上限**的保底调用资源，防止直接停用；该模式要使用低速率、最低处理优先级，允许明显更慢的等待/响应，不应无限免费或直接刻意 Thread.sleep。实际每员工与企业总额度上限、耗尽后是否拒绝/排队仍待量化。延迟变慢只是拥塞与队列/限速结果，不能用延迟本身当成成本控制。
2. **保底模型自动切换（2C）**：进入保底模式时，由平台**按 Agent 配置的保底逻辑模型**自动切换；它可能不同于员工正常手动选择的模型。这是明确且有限的例外，不能解释为正常模式自动跨模型路由。保底模型必须是该 Agent 被批准允许的模型且符合企业安全策略，需对客户端明确报告有效模型，若无允许的保底模型须定义降级失败处理。
3. **基础处理容量保障（3B）**：平台在自己可控的入口侧为低优先级/保底请求保留少量基础并发容量，超过可有界等待，尽力提供基础可用性。第三方 Provider 的响应能力不受 AIGate 完全控制，保底不能承诺无限等待或必然成功。
4. **三级流量档位（4，自定义）**：只有三个业务档位——**限流档、普通档、紧急档**；前者用于额度耗尽后的保底，默认普通，后者通过具体任务申请的有期限资源提升。档位可同时决定请求速率、最大并发、排队优先级，必须明确三者不是同一个概念。已在途的普通模型调用不强制终止，紧急请求优先争取可释放容量。紧急任务的可信身份/有效期/撤销/避免长期饥饿待细化。
5. **同逻辑模型多部署智能路由（5B）**：员工正常模式手动选择 Agent 允许的逻辑模型；AIGate 在该**相同逻辑模型**的多个健康部署间综合**健康、当前负载、成本、延迟、配置权重**路由。除保底模型的已批准切换外，不得自行改选不同逻辑模型。不同 Provider 部署同模型可能有不同成本/实际性能，路由策略需兼顾安全和结算精度；是否对错误做重试/故障切换另行决策，**路由不等于自动重试**。
6. **多层次压力监控与容量治理（6C）**：至少支持逻辑 Model 汇总 + 每个 ModelDeployment 的 QPS/RPM、并发、延迟、错误/429/超时、成本/点数等实测指标；提供历史趋势、阈值告警、供管理员进行扩容/缩容判断的容量分析与预测。能观测的是 AIGate 经手的请求，不得把这些数据伪称第三方 Provider 的真实 GPU 负载。是否进行自动扩缩容由后续真实运维能力决定，不因本次确认直接承诺。

### Confirmed routing/tier processing sketch

```text
双身份认证（Agent Application Key + Employee credential）
→ Agent/Employee Model 权限检查
→ 根据每员工×Agent免费、个人基础、已获团队补充点数判断预算状态
   ├─ 正常额度可用：保持员工所选逻辑 Model，默认普通档
   ├─ 紧急任务已获批准且有效：使用任务专属紧急档（合法模型范围不扩权）
   └─ 正常额度用完：进入限流档，按 Agent 预设保底逻辑 Model 切换；
                      使用企业公共保底预算，受每员工周上限+低速/低优先/基础容量限制
→ 在所选有效逻辑 Model 的健康 Deployment 中按成本/负载/延迟/权重路由
→ 出站前预留相应预算；请求完成按已确认真实 Token+价格结算，未知成本待核对
→ 记录 Model / Deployment / Employee / Agent / Task / 预算来源，发送额度与告警通知
```

**与前文的两个例外/冲突已经厘清**：
- 之前的“员工手动选模型、路由不跨逻辑模型”，**正常使用模式继续成立**；仅在额度耗尽转入企业保底时允许按 Agent 已批准的保底 Model 自动切换。
- 之前的“余额不足不拒绝”是保底的业务期望；保底周限额或全公司预算用尽、无安全合规模型、上游不可用/队列超时时，仍须明确最终处理方式，不能无条件保证成功或无上限成本。

**尚需最终产品与预算决策**：公司保底预算总上限、每员工每周上限、每日/周额度耗尽后的处理；最低速率/并发与可等待的最大时长；紧急任务如何提交流量身份/生效/撤销；Deployment 健康指标与定价来源以及报警策略；身份凭证由谁签发、周结算时区与积分精度。

**不要把本节固化成“必须立刻用 MQ/Redis 自动调度/预测模型”**：本轮只确认业务期待，所有技术架构和实施 Phase 后续基于最简可验证主流程决定。

## 2. Target Business Journey (proposed until remaining details confirmed)

```text
公司管理员纳管既有 Agent / 发布允许的模型与额度策略
→ 员工通过受信任身份使用 Agent（可有主团队与临时团队任务）
→ Agent 使用自身独立网关 Application 接入 AIGate
→ 网关可信确定 Agent + 实际员工 + 可选任务/团队归属
→ 检查 Agent 权限与所选 Model 是否准入
→ 检查 Agent 免费周额度 → 员工基础周额度 → 已获发放的有效团队补充额度 → 耗尽时适用受限保底规则
→ 确定任务优先级与同模型 Deployment 的实际资源路由
→ 向 Provider 发起统一模型请求
→ 采集真实 Token、价格、失败与时延、按员工/Agent/Team/任务归属记录
→ 出站前预留、完成后按可验证实际用量结算，未知用量待核对
→ 额度不足时员工向相应团队申请，负责人审批与调配团队池
```

**此流程是按第1.1～1.3节确认的目标业务草案**；预留、实际 Token 计费和失败待核对的原则已确定，但并发事务算法、周界边界、保底总池耗尽后的最终处理、任务认证仍需明确。不得把目标流程写成已实现功能。

## 3. Current Implementation vs Target

**已实现并验收（Phase 1~3）：** Team/Employee/Application 基础 CRUD，Provider/Model/Deployment 及默认 Deployment，Application API Key Runtime Bearer 认证，同步单模型转发，调用 SUCCESS/FAILED 脱敏最小元数据、管理最近历史及30天清理。

**尚未实现：** Agent 与 Application 的明确企业业务映射、可靠真实员工身份、跨团队成员/任务参与、周 Agent 免费额度/个人额度/团队额度池/审批、Token计费与费用流水、按模型多 Deployment 资源路由、优先资源调度、模型压力面板、安全模型准入与完整员工权限。

**历史 P4-T01 限流计划**：由总控 PAUSED；此前 V8/Application RPM/单 JVM token bucket ADR-004 暂时只作为候选设计，不得编码直到重设路线。

## 9. FinOps Cost Attribution — User Rule CONFIRMED; Calculation Method PROPOSED（2026-10-20）

**用户确认的归属业务规则**：“谁用就属于谁，不同团队分配出去的额度可以直接加入成本中。” 解释为 **消费归使用员工**、**额度发放的内部预算支出归发放 Team**。跨团队任务所属 Team 不替代实际 Employee，不按每次调用重新选择承担成本的团队；谁发放额度，成功发放时 Team pool 扣减以及团队内部额度支出立即确认。到期未消耗不返还、不冲销历史已发放支出（既定业务决议）。

**注意三种报表口径，不可作为同一个企业财务总成本相加：**
1. **员工实际使用积分（Employee Usage）**：根据确认的实际 Token 使用和当次生效的内部积分价格结算，按可信 employeeId 唯一归属；可按员工/Agent/Model/主团队维度查看，团队维度以“员工使用”命名。员工主团队更换后的历史归属快照处理属下阶段设计。
2. **团队已发放额度的内部预算支出（Team Grant Allocation Expense）**：成功发放的 grant.points 全额计入 issuerTeamId；无论收款员工是否属于该团队、是否后来用完，发放只产生一次团队额度池支出。消费 Grant 时减少员工 Grant 可用余额，**不再向发放 Team 重复记第二笔发放支出**。
3. **公司供应商实际模型调用成本估算（Provider Cost Estimate）**：确认的 input/output/cache 等 Token × 对应 Provider/Deployment 生效供应商计价版本，按币种和金额精度估算。由真实调用产生，与企业积分分配/充值不同；自部署算力成本需独立依据，估算不等于第三方最终账单。

**示例（示意数字，非真实项目数据）**：客服 Team 成功发放 1,000 积分给主团队为研发的 Employee；员工后续真实模型使用 300 积分。员工 Usage=300、研发团队员工使用视图=300；客服 Team 发放预算支出=1,000，池已扣 1,000；未用 700 到期不返还；全公司模型费用仅按实际确认 Token 与外部供应商价格另估算，**不能用 1,000+300=1,300 积分声称模型采购费用**。

**总控提出的最简计算方案（未获用户对公式的独立批准）**：
- `employee_usage_points = SUM(finalized_request_points WHERE employee_id=e)`
- `team_grant_budget_spend_points = SUM(successful_grant_issued_points WHERE issuer_team_id=t)`
- `company_provider_cost_estimate = SUM(confirmed_token_quantity × effective_provider_unit_price)`，每一计价维度分开相乘再求和，按币种分组，保留价格版本。
- **报表独立呈现**团队员工使用、团队对外发放的内部积分支出、实际外部 Provider 模型费。若管理层以后要求唯一“团队综合成本”列，须另行确认计费承担人/资金来源，避免内部转移的 Grant 发放和 Grant 消耗重复计入。

**已确认 vs 待确认**：员工/发放团队归属及发放即扣已确认；上面建议的报表公式、积分精度、Team 总成本聚合视图、历史主 Team 快照等为下阶段 P5/P6/P11 具体合同候选。当前 P4-T01 PAUSED / NO CODING。
