# AIGate — Enterprise AI Agent Governance: Confirmed Business Rules

> 总控维护的产品业务规则事实来源。2026-10-20 用户完成七项主体/额度/模型原则确认，**不等于相关功能已经实现**。仍有业务细则需要逐层讨论；Phase 4 编码保持 PAUSED。
>
> 项目定位：企业内部已有 Agent 的统一 AI 模型调用网关、员工额度/团队资源管理、模型安全准入与流量治理系统。AIGate 负责管理 Agent 的接入与模型流量，**不开发 Agent、不建设 Agent 注册细节、工作流编排器或 Agent 执行引擎**。

## 1. Confirmed Top-Level Principles

1. **统一网关入口**：纳入管理的企业 Agent 调用大模型必须经过 AIGate；这是公司治理规则，后续还需要凭证/网络出口等机制落实，不能声称软件接口天然杜绝绕过。
2. **员工+团队**：员工有一个主团队；有时被邀请参与其他团队任务，可以因此获得更多额度。跨团队任务的额度来源与审批归属尚待确认。
3. **Agent 纳管方式**：Agent 业务由外部系统开发/注册与运行，平台管理员统一管理纳管范围、接入规则/额度相关策略；不开发 Agent 注册的业务细节。
4. **Agent—Application**：按用户选择采用一对一；当前 Application 可以作为每个受管 Agent 的网关调用身份与规则载体。当前 Application 的 API Key 认证只证明 Agent/Application，不证明员工本人。
5. **调用人**：普通模型调用必须归属实际员工，额度按实际员工计算；定时/无人值守任务允许专门开账号进行独立管理。安全建议后续将该账号设计为明确的服务身份，而非假扮自然人；账户生命周期与可信认证尚待确认。
6. **周额度制度（已确认方向）**：有使用权限的员工使用不同 Agent 时有免费额度；先用对应 Agent 免费额度，超出后使用员工个人额度；个人额度不足可以向团队申请额外额度。用户尚未明确免费额度究竟按“每员工×Agent”分配、周结算/到期规则、额度计量单位、申请的团队归属及团队池冻结扣减机制，不能自行冻结数值/算法。
7. **紧急任务**：针对具体任务申请临时额外额度和有时效的优先处理权。优先处理需真正的容量/调度约束支持，不能仅存一个 priority 字段。
8. **模型权限**：每个 Agent 有几个由管理策略指定的允许模型选项，由员工在该 Agent 允许范围内手动选择；涉及安全与业务需求。
9. **路由语义**：自动路由主要用于**同一逻辑模型的多个 Deployment** 之间选择，不是在不同模型之间自行切换。当前 P2 仅有 Application.defaultDeploymentId，未来扩展要保留允许模型限制和逻辑模型选择的分离。
10. **模型价格与运行压力**：各模型有不同计费规则；管理员需要看到按模型运行压力与健康状态。网关能够观测自身请求量、延迟、并发、错误、Provider 限流，但不天然知道第三方 Provider 的实际 GPU 负载。

## 2. Target Business Journey (proposed until remaining details confirmed)

```text
公司管理员纳管既有 Agent / 发布允许的模型与额度策略
→ 员工通过受信任身份使用 Agent（可有主团队与临时团队任务）
→ Agent 使用自身独立网关 Application 接入 AIGate
→ 网关可信确定 Agent + 实际员工 + 可选任务/团队归属
→ 检查 Agent 权限与所选 Model 是否准入
→ 检查每周 Agent 免费额度 → 员工个人额度 → 已获审批的额外团队额度
→ 确定任务优先级与同模型 Deployment 的实际资源路由
→ 向 Provider 发起统一模型请求
→ 采集真实 Token、价格、失败与时延、按员工/Agent/Team/任务归属记录
→ 按实际消耗结算并向员工与管理员展示用量
→ 额度不足时员工向相应团队申请，负责人审批与调配团队池
```

**仅上述业务方向被确认**；调用前的费用预留/并发防超支、失败是否计费、跨周、团队归属与审批身份仍然是待定，不可当成已冻结的算法。无人值守任务单独账号也必须防止伪造其他员工身份。

## 3. Current Implementation vs Target

**已实现并验收（Phase 1~3）：** Team/Employee/Application 基础 CRUD，Provider/Model/Deployment 及默认 Deployment，Application API Key Runtime Bearer 认证，同步单模型转发，调用 SUCCESS/FAILED 脱敏最小元数据、管理最近历史及30天清理。

**尚未实现：** Agent 与 Application 的明确企业业务映射、可靠真实员工身份、跨团队成员/任务参与、周 Agent 免费额度/个人额度/团队额度池/审批、Token计费与费用流水、按模型多 Deployment 资源路由、优先资源调度、模型压力面板、安全模型准入与完整员工权限。

**历史 P4-T01 限流计划**：由总控 PAUSED；此前 V8/Application RPM/单 JVM token bucket ADR-004 暂时只作为候选设计，不得编码直到重设路线。

## 4. Next Business Decisions — Not Yet Confirmed

- 周额度边界：何时重置、免费额度按每个员工×Agent还是按 Agent 全体共享、个人周额度是否清零、团队额外额度是否到期。
- 额度单位：统一资源点数/金额还是 Token；不同 Model 的价格如何影响扣减；失败和输出时 token 成本如何结算。
- 员工临时参与其他团队任务的费用由主团队、借调团队还是本人承担；谁审批/负责团队预算。
- Agent 向网关传递实际员工身份的可信认证方式、服务账号的权限/归属与撤销机制。
- 被平台限流、额度不足、资源排队、Provider 错误如何在对外 HTTP/任务状态上区分；优先级和资源保障的有效期、可撤销性。
- Agent 的允许模型列表、各模型部署路由、切换与安全边界的详细规则。

产品业务确认顺序：顶层目标 → 主体归属（当前） → 额度/调用结算 → 模型与调度 → 全部 Phase 路线 → 各 Phase 架构/接口/测试。重要决策总控负责更新 docs；**开发导师不可修改 docs/**。
